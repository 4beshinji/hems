# W1.2 設計ノート（改訂）— `device_id` / `vendor_ref` 検証の backend/brain 統一

対象: [`PLAN.md`](PLAN.md) W1.2 のフォローアップ。2026-06-11 監査で「backend schemas と brain validator の間に齟齬がある」ことが判明したため、検証ルールを統一する。

---

## 1. 現状の齟齬

### 1.1 backend 側 (`services/backend/schemas.py`)

```python
DEVICE_REF_PATTERN = re.compile(r"^[\w.\-]+$")
MAX_DEVICE_REF_LEN = 128

def _validate_device_ref(value: str | None) -> str | None:
    if value is None:
        return None
    if len(value) > MAX_DEVICE_REF_LEN:
        raise ValueError(f"device ref too long: {len(value)} > {MAX_DEVICE_REF_LEN}")
    if not DEVICE_REF_PATTERN.match(value):
        raise ValueError("device ref contains invalid characters")
    return value
```

**問題**: `^[\w.\-]+$` は以下を許容する:
- 連続するドット (`a..b`)
- 先頭/末尾のドット (`.ab`, `ab.`)
- 空文字は `+` により拒否される

### 1.2 brain 側 (`services/brain/src/device_id_validator.py`)

```python
DEVICE_REF_PATTERN = re.compile(r"^[\w.\-]+$")
MAX_DEVICE_REF_LEN = 128

def is_valid_device_ref(value: str) -> bool:
    if not isinstance(value, str):
        return False
    if len(value) > MAX_DEVICE_REF_LEN or len(value) == 0:
        return False
    if not DEVICE_REF_PATTERN.match(value):
        return False
    if not all(value.split(".")):
        return False
    return True
```

**差分**: brain 側は `all(value.split("."))` により連続ドット・先頭/末尾ドットを拒否する。

### 1.3 齟齬が生じるシナリオ

1. ユーザーが `device_id = "living..room.sensor"` を backend へ heartbeat 送信
2. backend は `^[\w.\-]+$` で受け入れ、DB に登録
3. brain が MQTT 経由で同 device_id を受信し、`is_valid_device_ref` で拒否
4. 結果: dashboard にはデバイスが表示されるが、brain からの制御 dispatch が実行されない

---

## 2. 統一方針

### 2.1 採用ルール

brain 側の `all(value.split("."))` を canonical とし、backend schemas も同じ制約に寄せる。

**統一後のルール**:
- 正規表現: `^[\w.\-]+$`
- 最大長: 128 文字
- ドットセグメント: 各セグメントは空でない（連続ドット、先頭/末尾ドットを拒否）
- 空文字: 拒否

これは MQTT topic セグメントとして安全であり、`zigbee2mqtt/{device_ref}/set` のような topic 組み立て時に空セグメントを作らない保証にもなる。

### 2.2 共通化

現状 `services/brain/src/device_id_validator.py` と `services/backend/schemas.py` に同じ正規表現が独立して定義されている。共通化の選択肢:

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A | backend schemas が brain validator を import する | 単一ソース | backend → brain src への import 依存が逆（architecture 上 backend は上位） |
| B | `services/_common/hems_common/validation.py` に移動し両方から import する | 責務的に適切 | `_common` への依存増、brain も backend も `_common` 利用済みなので違和感なし |
| C | backend に同じロジックをコピーして同期テストで守る | 既存依存構造維持 | 重複は残る |

**推奨案: B**

`_common` は既に両方から使われており（brain は未だだが W3.1 で base イメージに同梱済み）、device ref 検証は明確に「共通 concern」である。

### 2.3 validator API

```python
# services/_common/hems_common/validation.py
import re

DEVICE_REF_PATTERN = re.compile(r"^[\w.\-]+$")
MAX_DEVICE_REF_LEN = 128


def is_valid_device_ref(value: str | None) -> bool:
    if not isinstance(value, str):
        return False
    if len(value) == 0 or len(value) > MAX_DEVICE_REF_LEN:
        return False
    if not DEVICE_REF_PATTERN.match(value):
        return False
    if not all(value.split(".")):
        return False
    return True


def validate_device_ref(value: str | None, field_name: str = "device_ref") -> str:
    if not is_valid_device_ref(value):
        raise ValueError(f"{field_name} must match ^[\\w.\\-]+$ with non-empty dot segments and <= {MAX_DEVICE_REF_LEN} chars")
    return value  # type: ignore[return-value]
```

backend schemas では Pydantic validator として `validate_device_ref` を使い、brain では `is_valid_device_ref` を使う。

## 3. backend パスパラメータ `device_id` の検証

### 3.1 問題

`DeviceControlRequest` 等の Pydantic schema に `device_id` が含まれていないため、`POST /devices/{device_id}/control` のパスパラメータ `device_id` は schema 検証を通らない。

### 3.2 対応

router 層でパスパラメータを検証する。FastAPI はパスパラメータを `str` として受けるため、依存関数または Path(...) で validator を適用する。

```python
from hems_common.validation import validate_device_ref
from fastapi import Path

@router.post("/devices/{device_id}/control")
async def control_device(
    device_id: str = Path(..., pattern=r"^[\w.\-]+$"),
    request: DeviceControlRequest = Body(...),
):
    validate_device_ref(device_id, field_name="device_id")
    ...
```

ただし `pattern` パラメータだけでは連続ドットを拒否できないため、router 内で `validate_device_ref(device_id)` を呼ぶことを推奨する。

## 4. 既存 DB 互換

### 4.1 startup 時 audit

backend `main.py` で既存 DB 内の不正値を warning 出力する処理がすでに存在する可能性を確認。存在しない場合は追加する:

```python
async def _audit_existing_device_refs(session):
    invalid = []
    for device in await session.scalars(select(Device)):
        if not is_valid_device_ref(device.device_id):
            invalid.append(device.device_id)
    if invalid:
        logger.warning("Existing devices with invalid refs: %s", invalid)
```

### 4.2 マイグレーション方針

既存データの強制修正は行わない。新規登録・更新時にのみ新ルールを適用し、既存不正値は運用中に段階的に修正する。これは PLAN.md W1.2 の当初方針と一致。

## 6. 受け入れ条件

- [ ] backend と brain で `device_id` / `vendor_ref` の受け入れルールが完全一致
- [ ] `a..b`, `.ab`, `ab.`, `a--b` 等の不正値が backend 登録時に拒否される
- [ ] `/devices/{device_id}/control` のパスパラメータも同じ検証を通る
- [ ] 既存 DB 内の不正値が startup 時に warning 出力される
- [ ] `make lint` 通過
- [ ] pytest baseline を下回らない
- [ ] MQTT auto-registration 経由の不正 ID も二層（backend + dispatch 直前）で拒否される

---

## 7. リスク

1. **既存デバイス登録の破壊**: 運用中に「backend では通っていたが brain では通らなかった」デバイスが新規登録拒否される。ただしこれはむしろバグ修正であり、 startup audit で可視化される。
2. **`_common` への依存増**: backend が `_common.validation` を import する。`_common` は base イメージに同梱済みであり、backend コンテナも `FROM hems-base` なので問題ない。
3. **正規表現の変更なし**: `^[\w.\-]+$` は維持。変更はドットセグメントの非空制約のみ。
