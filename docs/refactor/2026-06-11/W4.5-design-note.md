## 1. 設計: postgres を profile 不要のコアサービスに昇格

### 1.1 compose 変更(infra/docker-compose.yml)

1. **postgres から `profiles: ["postgres"]`(L511)を削除** → 常時起動のコアサービスに。
2. backend / brain の `depends_on` に postgres を追加(healthcheck 待ち):
   ```yaml
   depends_on:
     mosquitto:
       condition: service_healthy
     postgres:
       condition: service_healthy   # 既存 pg_isready healthcheck を利用
   ```
3. backend (L124) / brain (L65) の `DATABASE_URL` 既定を PG に切替(§2)。
4. SQLite opt-out を **compose profile ではなく env で表現**(理由: §1.3)。

### 1.2 SQLite を「軽量オプション」として温存する方式 — 推奨は env 切替

PLAN は「`--profile sqlite-lite` 相当」と書くが、**profile では実現しにくい**。理由: 同一 service(backend/brain)に profile 別の 2 定義を持たせると compose の service 重複でエラーになり、また「postgres を起動しない」を profile で表現するには postgres を再び profile gated に戻す必要があり、コア昇格と矛盾する。

**推奨: env フラグ `HEMS_DB=postgres|sqlite`(既定 postgres)で分岐**。compose の `DATABASE_URL` 既定式を以下のように二段 fallback にする:

```yaml
# backend / brain 共通
- DATABASE_URL=${DATABASE_URL:-${HEMS_DB_URL_DEFAULT:-postgresql+asyncpg://hems:${POSTGRES_PASSWORD}@postgres:5432/hems}}
```

SQLite に戻したいユーザーは `.env` で明示的に:
```bash
DATABASE_URL=sqlite+aiosqlite:///./data/hems.db
```
を 1 行書く(従来 PG ユーザーが書いていたのと対称)。postgres service は起動するが backend/brain が繋がないだけ、を避けたい場合は別 compose override(`docker-compose.sqlite.yml` で postgres を `profiles: ["never"]` 化 or `deploy.replicas: 0`)を用意する案もあるが、**初期実装では「SQLite 選択時も postgres コンテナは起動する(無害・低リソース)」を許容**し、override は将来 row に倒すのが blast radius 最小。

> 設計判断ポイント(ユーザー確認要 §7-A): 「SQLite opt-out 時に postgres コンテナを起動させないか(override 追加)/ 起動するが未使用を許容するか」。後者は実装が一気に軽くなる(profile 操作ゼロ)。

### 1.3 移行後の volume

PG コア化後、SQLite を使わないユーザーでも `hems_backend_data` / `hems_brain_data`(audio キャッシュ等も含む)は残す。`hems_pg_data` が新たな永続 SoT。

## 2. DATABASE_URL デフォルトの切替

### 2.1 backend (`services/backend/database.py` L25)

```python
# before
DATABASE_URL = os.getenv("DATABASE_URL", "sqlite+aiosqlite:///./data/hems.db")
# after
DATABASE_URL = os.getenv("DATABASE_URL", "postgresql+asyncpg://hems:hems@postgres:5432/hems")
```
同時に PG pool 設定を追加(db-improvement-plan §3 案A と統合 — この row で一緒に入れるのが自然):
```python
if "postgresql" in DATABASE_URL:
    _engine_kwargs |= {"pool_size": 5, "max_overflow": 5, "pool_pre_ping": True}
```
`main.py` L42 の `if "sqlite" in db_url:`(data dir 作成)は SQLite 時のみ走る分岐なので **そのまま温存で正しく動く**(PG 時はスキップされる)。

> 注: コード側の素の default に password を埋め込むのは compose env が常に上書きするので実害は薄いが、**compose env で渡すのを正**とし、コード default は「dev で env 無し起動」用の安全側。docker 経由なら必ず `DATABASE_URL` が注入される(§1.2)。

### 2.2 brain event_store (`services/brain/src/event_store/database.py` L203)

現状 `DATABASE_URL` 未設定 = event store 無効(L204-206 で warning + None)。**この挙動は維持**(brain は DB 無しでも ~10min 動く設計, backend CLAUDE.md 参照)。コードの default 変更は不要 — compose 側で `DATABASE_URL` を PG に向けるだけで自動的に PG init される(L208 の文字列判定がそのまま機能)。

### 2.3 env で SQLite に戻せること

`.env` に `DATABASE_URL=sqlite+aiosqlite:///./data/hems.db` を書けば従来通り。env.example にこの 1 行をコメントで案内(§6)。

## 3. SQLite→PG 移行スクリプト(infra/scripts/migrate_sqlite_to_pg.py)

### 3.1 配置と起動方法

- 配置: `infra/scripts/migrate_sqlite_to_pg.py`(既存 scripts 群と同居)。
- 実行(ホスト or 一時コンテナ):
  ```bash
  # dry-run(件数比較のみ、書き込みなし)
  python infra/scripts/migrate_sqlite_to_pg.py --dry-run
  # 実行
  python infra/scripts/migrate_sqlite_to_pg.py \
    --backend-sqlite /var/lib/docker/volumes/hems_backend_data/_data/hems.db \
    --brain-sqlite   /var/lib/docker/volumes/hems_brain_data/_data/hems.db \
    --pg postgresql+asyncpg://hems:$POSTGRES_PASSWORD@localhost:5442/hems
  ```
  既定パスは docker volume を自動探索 or env から導出。

### 3.2 3 系統の移行

| 系統 | ソース | 宛先 | 方式 |
|---|---|---|---|
| backend(tasks ほか 25 表) | `hems_backend_data/hems.db` | PG `public` schema | ORM メタデータ駆動 |
| shopping(`shopping_items`/`purchase_history`) | 同上(同一ファイル) | PG `public` | backend に含まれるので実質一括 |
| event_store(6 表) | `hems_brain_data/hems.db` | PG `events` schema | 生 SQL(DDL は init 済を前提) |

> **shopping は backend と同一 SQLite ファイル**(`models.py` の `ShoppingItem`/`PurchaseHistory` は Backend テーブル)。PLAN が「3 系統」と数えるのは論理的区分で、物理ソースは 2 ファイル(backend / brain)。スクリプトは 2 ファイル入力で 3 区分を扱う。

### 3.3 移行手順(スクリプト内ロジック)

1. **前提**: PG スキーマは既に存在(backend は app 起動の `create_all` で、brain は `init_db` の DDL で作られる)。スクリプトは **データ転送のみ**を担い、DDL は app に任せる(二重実装回避)。`--init` フラグで「app 未起動でも自前で create_all + DDL を流す」オプションも提供。
2. backend: SQLAlchemy の `Base.metadata.sorted_tables`(FK 依存順)を使い、各テーブルを SQLite から `SELECT *` → PG へ `INSERT`(`bulk_insert_mappings` or `executemany`)。
3. event_store: 6 テーブルを固定順(`world_events` → `llm_decisions`(FK cause_event_id)→ 他)で SELECT/INSERT。`data` 列は SQLite では TEXT(JSON 文字列)、PG では JSONB なので **文字列 → json.loads → JSONB cast**(`writer.py` の jsonb_cols 扱いと整合)。timestamp は naive(SQLite)→ UTC tz 付与(`TZDateTime` と同じ規約, database.py L19-22)。
4. SERIAL/BIGSERIAL の id: SQLite の id 値をそのまま挿入(`OVERRIDING SYSTEM VALUE` 不要、明示 id 指定で可)。移行後に `setval(pg_get_serial_sequence(...), max(id))` で sequence を進める(以後の auto-increment 衝突防止)。**これを忘れると移行直後の INSERT が PK 重複で落ちる — 必須**。

### 3.4 dry-run / 冪等性 / 無損失

- **dry-run**: 各テーブルの SQLite 件数を数え、PG の現件数と並べて表示。書き込みなし。差分の見積りに使う。
- **冪等性**: 既定は「**空の PG にのみ流す**」。各テーブルで PG に行が既にある場合は `--skip-nonempty`(既定)でスキップ、`--truncate-target` で明示削除後再投入、`--upsert`(id 衝突を `ON CONFLICT DO NOTHING`)を選択肢に。再実行で二重挿入しないことを保証。
- **無損失検証**: 移行後に全テーブルの件数照合(SQLite count == PG count)を出力。不一致は exit code != 0。`--verify-only` で照合のみ実行可。
- **トランザクション**: テーブル単位 tx(大量行の event_store は chunk insert + 中間 commit でメモリ抑制)。失敗時は当該テーブルを rollback、他は維持(部分再開可)。

### 3.5 commit 構造(本スクリプトと row 全体)

PLAN の 1 row = 1 commit 規律に沿いつつ、blast radius を分けるため **4 commit** を推奨:

| commit | 内容 | 検証ゲート |
|---|---|---|
| C1 | DATABASE_URL 既定切替 + PG pool 設定(database.py / event_store/database.py)。**compose は触らない** | 既存テスト(SQLite で env 明示)が緑。新規: PG 既定が読まれる unit test |
| C2 | compose: postgres コア昇格 + depends_on + DATABASE_URL 既定式 + SQLite opt-out 導線。`docker compose config` 検証 | `docker compose config` + 手動 `up -d` 疎通(PG 既定で backend/brain 起動) |
| C3 | `migrate_sqlite_to_pg.py`(dry-run / verify / 冪等)+ スクリプト単体テスト(temp SQLite → temp PG or sqlite-to-sqlite で論理検証) | スクリプトの unit/integration test |
| C4 | docs 整合(§6 の全ファイル)+ env.example | doc lint(リンク切れなし) |

C1→C2 は直列(C2 が C1 の既定に依存)。C3/C4 は C1 後なら並行可。

| 案 | 内容 | 評価 |
|---|---|---|
| **A(推奨)** | quickstart wizard / install.sh が `.env` 生成時に `POSTGRES_PASSWORD` も乱数化。手動 `docker compose up` 前に必ず `make quickstart` を通す導線に | distribution Phase 1 と完全整合。F3 を PG ごと解消。**W4.5' は Phase 1 と同期着手が必要** |

## 5. 後方互換・ロールバック

### 5.1 既存 SQLite ユーザーの移行パス(ドキュメント手順)

1. `git pull` 後、**まだ `up` しない**。
2. `.env` に `POSTGRES_PASSWORD` を設定(quickstart 経由 or 手動乱数)。
3. `docker compose up -d postgres` で PG のみ起動 → backend/brain も一度起動して空スキーマを作らせる(or スクリプトの `--init`)。
4. `python infra/scripts/migrate_sqlite_to_pg.py --dry-run` で件数確認。
5. 本実行 → verify。
6. 以後 PG 既定で全サービス起動。SQLite volume は当面保持(問題なければ後で削除)。

### 5.2 ロールバック

- 移行が失敗 / 不満なら `.env` に `DATABASE_URL=sqlite+aiosqlite:///./data/hems.db` を書き戻すだけで完全復帰(SQLite volume は無傷で残っている)。
- これが「SQLite 温存」の実質的なロールバック保険。**移行スクリプトは SQLite を読むだけで書き換えない**(無損失の片方向)ことを保証 → ロールバックが常に安全。

### 5.3 互換性の落とし穴(実装者向け注意)

- backend と brain で SQLite ファイルが別(§0.4)。移行スクリプトに **両方のパスを渡し忘れると brain event_store が空のまま PG 化**される。dry-run で両ソースの件数が出ることを必須チェックに。
- `llm_decisions.cause_event_id` の FK(`world_events.id`)— event_store 移行は `world_events` を先に入れる順序必須(§3.3)。
- timestamp の tz: SQLite naive → PG TIMESTAMPTZ。UTC 付与を統一(`TZDateTime` 規約)。ずれると retention DELETE(730d cutoff)や集計の時刻境界が狂う。

## 7. リスクと、実装 GO 前にユーザー判断が要る点

### 7.1 リスク

| リスク | 深刻度 | 緩和 |
|---|---|---|
| 既存稼働データの移行事故 | 高 | dry-run 必須化、件数 verify、片方向(SQLite 無改変)、ロールバック容易(§5.2)。brain/backend 2 ソースの取りこぼし注意 |
| PG 必須化による初回体験劣化 | 中〜高 | distribution Phase 1 quickstart と同期(§4.2 案A)。先行する場合は README 明記 |
| **CI への影響** | 中 | §7.2 参照 |
| id sequence 未更新で移行後 INSERT 衝突 | 中 | `setval` を移行スクリプトに必須実装(§3.3-4)。verify に「PG への試験 INSERT」を含めても良い |
| SQLite opt-out 時に postgres が無駄に起動 | 低 | 初期は許容(§1.2)。override は将来 row |
| JSONB / timestamp 変換の取りこぼし | 中 | event_store の `data` 列・timestamp tz を明示変換(§5.3) |

### 7.2 CI への影響

- **現状 CI は SQLite で全テスト**(`.github/workflows/ci.yml` `test-backend` job、各 test が `monkeypatch.setenv("DATABASE_URL", "sqlite+aiosqlite://...")` で個別に SQLite 指定。postgres service コンテナは CI に無い)。
- DATABASE_URL の **コード default を PG に変えても、テストは env を明示上書きしているので CI は壊れない**(grep 済: tests 全てが SQLite URL を setenv)。→ **CI は基本そのまま緑**。
- ただし「PG 既定が正しく読まれる」テストを追加する場合、(a) default 文字列を読む unit test(接続せず文字列検証)で済ませる、(b) PG での実 DDL/migration/移行スクリプトを回すには CI に `services.postgres`(GitHub Actions service container)を追加する必要がある。**移行スクリプトの integration test を CI に乗せるなら postgres service 追加が必要**(`docker-build` job とは別)。これは新規ジョブで、既存 SQLite テストには非干渉。
- 推奨: C1/C2 は文字列レベル + `docker compose config` で CI 完結。C3 の移行スクリプト integration test のみ、PG service container 付きの新ジョブ(または integration marker で手動)に隔離。

### 7.3 実装 GO 前にユーザー判断が要る点

- **A. SQLite opt-out 時に postgres コンテナを起動させないか**(§1.2): 起動許容(実装軽い・推奨)/ override で停止(クリーンだが追加実装)。
- **B. distribution Phase 1(quickstart)との順序**(§4.2): Phase 1 完了後に着手(zero-config を犠牲にしない・推奨)/ 先行して暫定的に「`POSTGRES_PASSWORD` 手動 1 行」を要求。**「zero-config をどこまで犠牲にするか」の本丸はここ**。完全 zero-config(コマンド 0 設定 0)は PG 既定では不可能 — 最低限「パスワード生成」が要る。案 A(quickstart で自動乱数化)なら体感ゼロ設定を維持できるが、quickstart 実装が前提。
- **C. CI に PG service container を足すか**(§7.2): 移行スクリプトの integration test を CI で回すか、手元/integration marker に留めるか。
- **D. id sequence 移行の verify をどこまで厳密にするか**: setval だけで足りるとみなすか、移行後に試験 INSERT で実検証するか。

PG 両対応コードは既存。本 row は **(1) DATABASE_URL 既定を PG へ + pool 設定 → (2) compose で postgres をコア昇格 + depends_on → (3) 片方向・dry-run・冪等な SQLite→PG 移行スクリプト → (4) docs 整合** の 4 commit。SQLite は `DATABASE_URL` 上書きで温存。zero-config の毀損は distribution Phase 1 の quickstart 乱数化に `POSTGRES_PASSWORD` を相乗りさせて回避するのが正道で、**Phase 1 との順序がユーザー判断の本丸**。CI は env 明示上書きのおかげで基本無傷、移行スクリプトの PG integration test だけ隔離ジョブを検討。
