## 2. 調査 2 — vendor 間の共通処理と固有処理

### 共通(全 vendor 横断)
- **device_id / vendor_ref の検証**(W1.2): `dispatch` 入口 L587、各 `_dispatch_*` 入口 L682/L705/L747 で `is_valid_device_ref`。固定 error message 形式 `Invalid vendor_ref {ref!r}: must match ^[\w.\-]+$`。
- **vendor_ref 解決パターン**: `device.get("vendor_ref") or device.get("device_id","").replace("{vendor}.","")`(L621, L680, L703, L745)。**4 箇所で複製**。
- **bridge 未設定ガード**: `if not XXX_BRIDGE_URL: return {"success": False, "error": "... not configured"}`(ha/switchbot/tapo)。zigbee は `mqtt_client is None` 判定。
- **返り値契約**: 全経路 `{"success": bool, "result"|"error": str}`。
- **action / capability guard**: `dispatch` core が `ALLOWED_ACTIONS` + `_ACTION_CAPABILITY` で一括(L599–603)。各 vendor parser は cmd マップに無い action を二次的に弾く(`_ha_service_for` 等が `None` 返し)。

### 固有(vendor ローカル)
- **pulse**(ON→OFF): tapo は同期 sleep ベース(`await asyncio.sleep`, L717)、zigbee は `loop.call_later` 非ブロック(L763)。ha/switchbot は pulse 非対応。**実装方式が vendor で異なる**(blast radius 要注意)。
- **rainbow**: ha は `asyncio.ensure_future` で hue cycling(L629, `_ha_rainbow`)、zigbee は `loop.call_later` ×steps + warm white 復元(L774–802)。switchbot/tapo 非対応。
- **topic / cmd 組み立て**: ha=service 文字列(`light/turn_on` 等), switchbot=`(command, parameter, command_type)` triple, zigbee=JSON payload dict, tapo=`turnOn/turnOff/toggle` 文字列。
- **正規表現**: parse 側のみ。`_IEEE_ADDR_RE`(L389, zigbee 固有)。topic は `split("/")` ベースで regex 不使用。

## 3. 調査 3 — 発火順序・副作用・エラー処理

- `dispatch` の順序: ①device_id 検証 → ②`lookup`(HTTP) → ③未登録なら error → ④`ALLOWED_ACTIONS` チェック → ⑤`_ACTION_CAPABILITY` チェック → ⑥vendor 分岐。**この順序は挙動契約**(検証は I/O 前)。
- HTTP timeout: lookup/list=5s, ha/switchbot/tapo control=15s, rainbow step=5s。
- error 整形: bridge レスポンスは `data.get("detail", f"HTTP {resp.status}")`。`_tapo_raw` のみ try/except で例外→error 文字列化(他は例外を握らず上位伝播の可能性)。
- mcp は dispatch 非対応で固定 error(L614, `send_device_command` tool 経由を案内)。
- **副作用の純粋性**: parse_mqtt 系は純関数(I/O なし)→ characterization が容易。dispatch 系は session/mqtt_client への副作用 → mock で観測。

## 5. ALLOWED_ACTIONS 改名方針

- 改名: `ALLOWED_ACTIONS` → **`DEVICE_ALLOWED_ACTIONS`**(device actuator action の allowlist であることを明示)。
- 影響箇所(全網羅):
  1. `device_dispatcher.py` 定義(L832)+ 内部参照 `dispatch`(L599)。
  2. `device_control_validator.py` L26 の `from device_dispatcher import ALLOWED_ACTIONS` → `DEVICE_ALLOWED_ACTIONS`(関数内 import, L29 の参照も)。
  3. test: 現状 `ALLOWED_ACTIONS` を直接 import するテストは無し(grep 確認済)。`test_device_control_validation.py` は `validate_device_control` 経由でのみ間接利用 → **改名で test 修正不要**。
- sanitizer 側 `_ALLOWED_BROWSER_ACTIONS`: 現状は `_validate_control_browser` 内のローカル変数名 `_ALLOWED_ACTIONS`(sanitizer.py L420)。**module-level 定数化 + `_ALLOWED_BROWSER_ACTIONS` への改名**を W3.4 のスコープに含め、device 側との名前衝突懸念を物理的に解消する(任意だが監査意図に合致)。最小スコープに留めるなら sanitizer 変更を C3 として分離可。
- 移行配慮: 後方互換が必要なら一時的に `ALLOWED_ACTIONS = DEVICE_ALLOWED_ACTIONS` の alias を残す案もあるが、import 元が 1 箇所のみで grep 完全把握できるため **alias 不要・一括改名**で良い。

## 6. 設計 — vendor parser クラス群への分割

### 6.1 配置(`rules/` 類似の `vendors/` サブパッケージ)

```
services/brain/src/
  device_dispatcher.py        # 縮小: DeviceDispatcher core + 公開 re-export のみ
  devices/
    __init__.py               # 公開 API re-export(後方互換 facade)
    observation.py            # DeviceObservation dataclass + _SENSOR_CHANNEL_UNITS
    actions.py                # DEVICE_ALLOWED_ACTIONS, _ACTION_CAPABILITY
    registry.py               # VENDOR_PARSERS = {"ha": HAParser(), ...} 登録テーブル
    base.py                   # VendorParser ABC(parse / dispatch / build_command の I/F)
    vendors/
      ha.py                   # HAParser
      switchbot.py            # SwitchBotParser
      tapo.py                 # TapoParser
      zigbee.py               # ZigbeeParser + parse_z2m_bridge_devices + Z2M helpers
      mcp.py                  # McpParser(parse のみ; dispatch は非対応 error)
```

注意: `device_dispatcher.py` を残し、そこから `from devices import *` 相当で **公開シンボル(`DeviceDispatcher`, `parse_mqtt`, `parse_z2m_bridge_devices`, `DEVICE_ALLOWED_ACTIONS`)を re-export** する facade を維持すれば、`brain_mqtt.py` / `brain_startup.py` / `main.py` / test の import 文を**一切変更せず**に済む(blast radius 最小化)。`device_control_validator.py` のみ `ALLOWED_ACTIONS`→`DEVICE_ALLOWED_ACTIONS` の改名追従が必要。

### 6.2 VendorParser インターフェース(案)

各 vendor の責務を 2 系統に分ける:

```python
class VendorParser(ABC):
    vendor: str
    # --- parse 系(純関数, MQTT → observation) ---
    def matches(self, parts: list[str]) -> bool: ...
    def parse(self, parts: list[str], payload: dict) -> DeviceObservation | None: ...
    # --- dispatch 系(副作用, action → bridge) ---
    async def dispatch(self, ctx: DispatchContext, device: dict, action: str, params: dict) -> dict: ...
```

- `parse_mqtt(topic, payload)` は registry を回して最初に `matches` した parser の `parse` を呼ぶ薄い関数に縮小。
- `DispatchContext`: `session` / `mqtt_client` / bridge URL 群 / `resolve_ref()`(共通の vendor_ref 解決 + W1.2 検証)を保持。**§2 の重複 vendor_ref 解決を 1 箇所に集約**する受け皿。
- zigbee dispatch は同期だが I/F 上 `async def` に揃え、内部で同期 publish + `loop.call_later`(挙動不変)。`zigbee_permit_join` は zigbee 固有メソッドなので `ZigbeeParser` か `DeviceDispatcher` に専用メソッドとして残す(tool dispatch が直接呼ぶため公開維持)。

### 6.3 共通処理(cooldown/pulse/validation)の置き場
- **vendor_ref 解決 + W1.2 検証**: `DispatchContext.resolve_ref(device, vendor)` に集約。各 parser はこれを呼ぶだけ。
- **bridge 未設定ガード**: 各 parser の `dispatch` 冒頭(URL/mqtt_client は ctx 経由)。
- **action/capability guard**: `DeviceDispatcher.dispatch`(core)に残す。vendor 分岐前の共通チェックなので parser に降ろさない。
- **pulse / rainbow**: 各 vendor で実装方式が異なるため **vendor parser 内に留める**(共通化すると tapo の sleep vs zigbee の call_later の差異を吸収できず挙動が変わるリスク)。共通化は今回スコープ外と明記。

### 6.4 新 vendor 追加が「1 ファイル追加」で済むか(拡張性確認)
- 新 vendor = `vendors/foo.py` に `FooParser(VendorParser)` を 1 個書き、`registry.py` の `VENDOR_PARSERS` に 1 行登録するだけ。`parse_mqtt` の if 連鎖編集も `dispatch` の `if vendor == ...` 編集も不要 → **目標達成**。
- ただし新 action 追加時は `actions.py` の `DEVICE_ALLOWED_ACTIONS` / `_ACTION_CAPABILITY` と `device_control_validator.py` の param 検証の更新が引き続き必要(これは設計上妥当な単一責務)。

### 7.3 characterization テスト具体案(C1, 分割前に作成)

新規 `tests/test_device_dispatcher_characterization.py`。`MagicMock(spec=aiohttp.ClientSession)` + mqtt mock(既存 `test_device_id_validation.py` の `_make_dispatcher` パターンを流用)で、**分割前の現行コードに対して**以下を pin する:

A. **parse_mqtt happy-path**(6 vendor): 代表 topic+payload → `DeviceObservation` の全 field(device_id/vendor/kind/device_class/capabilities/channels/units/last_state/last_value/battery_pct/link_quality)を assert。`test_device_id_injection.py` の valid-topic を拡張して field を厳密化。
B. **parse_z2m_bridge_devices**: 代表 `bridge/devices` payload(light + sensor + 命名済 friendly + raw IEEE)→ observation list の display_name / capabilities / channels を pin。`_z2m_friendly_display` の分岐(friendly 優先 / desc / model / IEEE 末尾付与)を網羅。
C. **dispatch → publish/POST pin**:
  - ha: `lookup` を AsyncMock で device 固定 → `session.post` の `call_args`(URL=`/api/device/control`, json の entity_id/service/data)を action 別(on/off/toggle/set_brightness/set_color_temp/set_color_xy/set_color_hs/set_position/set_temperature)に assert。
  - switchbot: POST body の `(command, parameter, command_type)` を action 別に assert(ir_send 含む)。
  - tapo: `turnOn/turnOff/toggle` の POST と **pulse の 2 連 POST 順序**(turnOn → sleep → turnOff)を `asyncio.sleep` を patch して assert。

D. **action/capability guard**: capability 不足時の error、未知 action の error を pin。
E. **error 整形**: bridge 4xx 時の `detail` 抽出、`_tapo_raw` の例外→error 文字列を pin。

これらが緑のまま分割すれば挙動不変を担保できる。

**リスク / 落とし穴**
- **W1.2 検証の移設**: `is_valid_device_ref` 呼び出しを `DispatchContext.resolve_ref` に集約する際、**検証が I/O より前**という順序を崩さない。error message 文字列を変えると `test_device_id_validation.py` の `"Invalid vendor_ref"` / `"Invalid device_id"` assert が割れる → 文字列保存。

- **`device_control_validator` の関数内 import**: 循環 import 回避の意図。facade の `devices/actions.py` へ `DEVICE_ALLOWED_ACTIONS` を置き、validator はそこから import するのが循環的に安全(`device_dispatcher` 経由でも facade re-export なら可)。
- **W2 整合**: W2 で他モジュール整理済。`devices/` の命名が W2 で導入した規約(rules/ 等)と衝突しないか確認。
- parse_mqtt の if 連鎖を registry の `matches` ループに置換する際、**マッチ順序**(現状の上から順 early-return)を保つ。特に zigbee の `bridge` 除外(L137)と ha の `len(parts)>=6` 条件の優先順を崩さない。

## 10. 実装 GO 前にユーザー判断が要る点

1. **分割の粒度**: §6.1 の `devices/` フルパッケージ(parser ABC + registry)か、より軽量に「parse 関数群 / dispatch 関数群を 2 ファイルに割るだけ」か。前者は拡張性目標(1 ファイル追加)を満たすが行数移動が大きい。後者は安全だが「新 vendor=1 ファイル」を完全には満たさない。**推奨は前者(VendorParser 登録テーブル)**。
2. **sanitizer の `_ALLOWED_BROWSER_ACTIONS` 改名を W3.4 に含めるか**(C3 として)、別 row に切るか。監査指摘の文面に追従するなら含める。
3. **facade 維持の是非**: `device_dispatcher.py` を re-export facade として残す(import 不変・低リスク)か、import 文も全面 `from devices import ...` に書き換える(クリーンだが blast radius 増)か。**推奨は facade 維持**。
4. **C2 の手動疎通の範囲**: 実機(zigbee stick / HA)が無い環境では mock 疎通のみで GO とするか。物理操作回帰は test で覆えないため、ここがユーザーのリスク許容判断。
5. **後方互換 alias**: `ALLOWED_ACTIONS = DEVICE_ALLOWED_ACTIONS` の一時 alias を残すか(import 元 1 箇所のため不要と判断, §5)。外部スクリプトが参照する可能性があるなら残す。
