# W2.6 design note — `_process_mqtt` god-function 分割

対象: `services/brain/src/brain_mqtt.py` の `MqttSyncMixin._process_mqtt`(L78–318, 約 240 行)。
元 row: 2026-05-25 LEDGER R5.1 / 本計画 [`PLAN.md`](PLAN.md) W2.6(難度 高 / Opus 4.8)。
依存: なし(W2.2 で `mqtt_router.py` は DI 済み = `MqttRouterMixin.update_from_mqtt`)。
**本 note は調査・設計のみ。コード変更は含まない。**

---

## 0. 結論サマリ

- `_process_mqtt` は **9 個の独立ステップ**の直列実行。ステップ間のデータ依存は実質 1 本のみ(enrich → `update_from_mqtt`)で、残りは互いに副作用を共有しない。よって機械的に抽出メソッドへ分割可能。
- ただし **順序保存が必須な箇所が 3 つ**ある(後述 §2)。とくに「Z2M enrich は `update_from_mqtt` より前」「`wake_up_fired` の集約 → sunrise 停止」「末尾の `_cycle_triggered` 判定は全 world_model 更新の後」。
- `_process_mqtt` への**直接テストは現状ゼロ**(§3)。分割の安全弁は characterization テストの先行追加。これがないと回帰を検出できない。
- **commit 分割を推奨**: (C1) characterization テスト追加 → (C2) 抽出。理由は §5。

## 1. 現状構造 — 9 ステップの境界

`brain_mqtt.py` 行番号で示す。`on_message`(L33–76)は分割対象外(ここでの制御トピック処理 + `call_soon_threadsafe` ディスパッチはそのまま)。

補足:
- S0 は `payload` を**変更してから** S1 に渡す。S1 の `update_from_mqtt`(`mqtt_router.py` L37–39, camera 分岐等)は enrich 済み payload を読む可能性があるため、S0→S1 順は固定。
- S5・S7 はどちらも camera person count を読むが**互いに独立**(S5 は occupancy 学習、S7 は wake トリガ)。同一 topic で両方発火しうる。
- S8 内の analog 検証は `mqtt_router.py` L19–27 の検証と **二重に走る**が、対象が別(S1=fusion 拒否、S8=event_store 拒否)。挙動として正しいので保存する。

## 2. 順序・冪等性 — 分割で壊れやすい箇所

分割で**順序を保存しなければならない**依存:

1. **S0 → S1**(必須): enrich は world_model 更新の前。逆転すると zone なしで fusion される。
2. **S7 内の集約 → sunrise 停止**(必須): `wake_up_fired` は biometric 経路(L160–172)と camera 経路(L174–191)の**論理和**。両経路を別メソッドに割っても、`wake_up_fired` の集約結果を sunrise 停止(L194–195)へ渡す構造を保つこと。安易に「経路ごとに sunrise を停止」にすると、片経路だけで停止判定が二重評価され、`is_active` ガードで実害はないが意味が変わる。**集約フラグを返す関数**にするのが安全。
3. **全 world_model 更新(S1, S5 の reconcile)→ S9 末尾の cycle-trigger**(必須): `_cycle_triggered.set()` の判定(L302–318)は `world_model.zones[].events` 等の長さ差分。S1/S5 が events を増やした**後**に評価する必要がある。S9 は最後に置く。

順序が**結果に影響しない**(自由に並べ替え可)もの:
- S2 / S3 / S4 / S6 は互いに独立。発火条件 topic が重ならない or 副作用先が別。
- S8 の record_sensor / record_world_event は S1〜S7 と独立(event_writer のみ触る)。

冪等性に関する注意:
- S9 の `_heartbeat_debounce`(10s)と `event_writer.record_world_event` の payload digest dedupe(5min, L228–229 コメント)は**呼び出し側の状態に依存**する非冪等処理。抽出後も `self._heartbeat_debounce` を共有 self 経由で参照するため問題なし。引数渡しにして state を複製しないこと。
- S0 の in-place payload 変更は後続ステップ全部が同じ dict を見る前提。抽出メソッドにも**同じ dict 参照**を渡す(コピーしない)。

スレッドモデル: `_process_mqtt` は `on_message`(MQTT スレッド)から `call_soon_threadsafe` 経由で **event loop スレッド上で**実行される(L75–76)。抽出メソッドも同一スレッドで直列に呼ばれるので、追加の同期は不要。

## 3. テストカバレッジの実態

grep 結果(`tests/`, `services/brain/tests/`):

- `_process_mqtt` を**直接呼ぶテストは存在しない**。唯一の言及は `tests/test_sensor_validation.py:5` の docstring で、「event-store persistence path lives in main.py::_process_mqtt and gets its integration test once the brain mixin split (Wave 5) makes it isolable」と**明示的に先送り**されている。
- `brain_mqtt` / `MqttSyncMixin` / `on_message` を import / 参照するテストもゼロ。
- 既存テストがカバーするのは **S1 の中身(`world_model.update_from_mqtt`)のみ**: `tests/test_world_model_mqtt_routing.py` ほか 14 ファイルが `update_from_mqtt` を叩く。これらは `MqttRouterMixin`(W2.2 で分離済)を守るが、**`_process_mqtt` 固有の S0/S2–S9 はノーカバレッジ**。
- PLAN.md W2.8 も「`brain_mqtt` は現状テストゼロ」と明記。

結論: **分割の前に characterization テストが必須**。これが W2.6 の唯一の安全弁。

## 4. `_process_mqtt` ↔ `mqtt_router.py` の責務境界

W2.2 で分離済の `MqttRouterMixin.update_from_mqtt`(`services/brain/src/world_model/mqtt_router.py` L7–129)との境界は**既に明確で、本 row では動かさない**:

- `mqtt_router.py` = **world_model state の純粋更新**(zone/pc/home/gas/news/weather/shopping/personal/tapo/zigbee へのルーティング)。外部 subsystem を一切知らない。テスト厚い。
- `_process_mqtt`(S0, S2–S9)= **world_model 更新の前後に走る orchestration**: enrich、subsystem feed(schedule_learner / event_automation / shopping_classifier / timeline)、event_store persist、device registry、cycle trigger。これらは `Brain` インスタンスの subsystem 参照を必要とするため `MqttSyncMixin` 側に残る。

すなわち W2.6 は **`mqtt_router.py` には触らない**。`brain_mqtt.py` 内の orchestration を分割するだけ。S1 は `self.world_model.update_from_mqtt(...)` の一行呼び出しのまま残す。

## 5. 抽出設計

### 5.1 抽出メソッド一覧(`MqttSyncMixin` の private メソッドとして)

すべて `(self, topic: str, payload, parts: list[str])` を基本シグネチャとし、`_process_mqtt` がオーケストレータとして順に呼ぶ。`parts = topic.split("/")` は冒頭で 1 度だけ計算して各メソッドへ渡す(現状は各ブロックで重複 split しているのを統合 — **挙動不変**)。

| 抽出メソッド | 由来 | 入力 | 出力 / 副作用 | 備考 |
|---|---|---|---|---|
| `_enrich_payload(topic, payload)` | S0 | topic, payload | payload を in-place 変更(返り値なし) | dict ガードは内部 |
| `_feed_shopping_classifier(topic, payload)` | S2 | 〃 | coroutine schedule | classifier+`_loop` ガード内包 |
| `_trigger_timeline_on_event(topic, parts)` | S3 | topic, parts | `_trigger_timeline_regen` schedule | timeline_generator ガード内包 |
| `_mark_intervention(topic, parts)` | S4 | topic, parts | event_writer state | |
| `_feed_schedule_learner_occupancy(topic, payload, parts)` | S5 | 全部 | reconcile + update_occupancy | inferred 計算ロジックを内包 |
| `_feed_schedule_learner_sleep(topic, payload)` | S6 | topic, payload | record_sleep | |
| `_detect_wake_up(topic, payload, parts) -> bool` | S7 (L160–191) | 全部 | coroutines schedule、**`wake_up_fired` を返す** | sunrise 停止は**含めない**(呼び出し側で集約フラグを使う) |
| `_record_to_event_store(topic, payload, parts)` | S8 | 全部 | event_writer persist | analog 検証 + record_sensor + record_world_event |
| `_update_device_registry(topic, payload, parts)` | S9 (L280–300) | 全部 | heartbeat / annotate / auto-reg | debounce は self 経由 |
| `_maybe_trigger_cycle()` | S9 (L302–318) | なし | `_cycle_triggered.set()` | env フラグ分岐含む |

`_process_mqtt` 本体は以下の薄いオーケストレータになる(擬似):

```
parts = topic.split("/")
self._enrich_payload(topic, payload)            # S0  (must be before S1)
self.world_model.update_from_mqtt(topic, payload)  # S1
self._feed_shopping_classifier(topic, payload)  # S2
self._trigger_timeline_on_event(topic, parts)   # S3
self._mark_intervention(topic, parts)           # S4
self._feed_schedule_learner_occupancy(...)      # S5
self._feed_schedule_learner_sleep(topic, payload)  # S6
woke = self._detect_wake_up(topic, payload, parts)  # S7
if woke and self.sunrise_alarm and self.sunrise_alarm.is_active:
    self.sunrise_alarm.stop(self.client)        # S7 集約 → 停止 (順序保存)
self._record_to_event_store(topic, payload, parts)  # S8
self._update_device_registry(topic, payload, parts) # S9a
self._maybe_trigger_cycle()                     # S9b (must be last)
```

ガード条件(`if self.X and self._loop`)は各抽出メソッドの先頭に early-return として移す。これにより本体は「全ステップを毎回呼ぶ」だけになり、**読み手は順序のみを追える**。

### 5.2 順序/副作用の保存方針

- S0→S1→…→S9 の**記述順 = 実行順**を本体で保証(§2 の必須 3 依存はこの並びで自動的に満たされる)。
- `wake_up_fired` は `_detect_wake_up` の**戻り値**として外に出し、sunrise 停止は本体で評価(§2-2)。
- `_maybe_trigger_cycle` を**最後**に固定(§2-3)。
- `parts` を一度だけ計算して渡すのは可読性改善であり、各ブロックの `len(parts) >= N` ガードはそのまま移植するので挙動不変。

## 6. characterization テスト方針(W2.6 の安全弁)

### 6.1 方針

分割**前**に、`_process_mqtt` の外部から観測可能な振る舞いを固定するテストを `tests/test_brain_mqtt_characterization.py` に新規作成する。`Brain` 全体は重いので、`MqttSyncMixin` だけを mock subsystem で構成した軽量 harness を使う:

- 実 `WorldModel()` インスタンス(conftest の `world_model` fixture を再利用)を `self.world_model` に注入。S1/S5/S9 の world_model 連動を実物で観測できる。
- `schedule_learner` / `event_automation` / `automation_engine` / `event_writer` / `shopping_classifier` / `timeline_generator` / `device_registry` / `dashboard` / `sunrise_alarm` は `MagicMock` / `AsyncMock`(conftest に既に import 済)。**呼ばれたか / 引数**を観測点にする。
- `self._loop` は `asyncio.get_event_loop()` の実ループ、または `call_soon_threadsafe` / `run_coroutine_threadsafe` を MagicMock 化して「スケジュールされた呼び出し」を捕捉(後者が決定的で推奨)。
- `_device_zone_map` / `_heartbeat_debounce` / `_last_event_count` / `_cycle_triggered` は手で初期化。

harness 例(設計のみ):
```python
class _Harness(MqttSyncMixin):
    def __init__(self, world_model):
        self.world_model = world_model
        self.schedule_learner = MagicMock()
        self.event_automation = MagicMock()
        self.automation_engine = MagicMock()
        self.event_writer = MagicMock()
        self.shopping_classifier = MagicMock()
        self.timeline_generator = MagicMock()
        self.device_registry = MagicMock()
        self.dashboard = None  # device-registry push を抑止したいケース用
        self.sunrise_alarm = MagicMock(is_active=True)
        self.client = MagicMock()
        self._loop = MagicMock()           # call_soon_threadsafe / run_coroutine_threadsafe を観測
        self._device_zone_map = {"0x1234": "living"}
        self._heartbeat_debounce = {}
        self._last_event_count = {}
        self._cycle_triggered = asyncio.Event()
        self._z2m_bridge_devices_pending = None
```

`run_coroutine_threadsafe` は `brain_mqtt` モジュール内の `asyncio.run_coroutine_threadsafe` を monkeypatch して、(coro, loop) を記録 + coro を close する。これで「どの coroutine がスケジュールされたか」を引数の関数名で検証できる。

## 7. commit 分割

**2 commit を推奨**:

- **C1 = characterization テスト追加のみ**(`tests/test_brain_mqtt_characterization.py` 新規 + harness)。コード本体は無改変。これ単体で現状の `_process_mqtt` に対して green になることを確認 = 「現挙動の固定」を独立した履歴に残す。
- **C2 = 抽出**(`brain_mqtt.py` の `_process_mqtt` を §5 のメソッド群へ分割)。C1 のテストが無改変で pass することがレビュー基準。

1 commit にまとめない理由: テストと実装を同 commit にすると「テストが新挙動に合わせて書かれた / 後付け」の疑念を排除できず、characterization の意味(=変更前の振る舞いを先に固定)が失われる。履歴上 C1 が C2 の前にあることが安全弁の証跡になる。

W2.8(各抽出単位への unit test)は C1 の characterization で実質前倒しされる。C2 後に「抽出メソッド単体の細粒度テスト」を足したい場合は W2.8 commit で追加(任意・本 row の必須ではない)。

## 8. 触るファイル・回帰リスク・落とし穴

触るファイル:
- `services/brain/src/brain_mqtt.py`(C2、`_process_mqtt` 分割。`on_message` / `_annotate_z2m_devices` / `_publish_mqtt` は不変)
- `tests/test_brain_mqtt_characterization.py`(C1 新規)
- `tests/test_sensor_validation.py`(任意・docstring の「Wave 5 で isolable」記述を更新、C2)
- `mqtt_router.py` は**触らない**(§4)

回帰リスク:
1. **`wake_up_fired` 集約の取りこぼし**(§2-2)。`_detect_wake_up` を bool 返り値にし、sunrise 停止を本体に残すことで回避。S7 専用テスト(wake→stop / no-wake→維持)で固定。
2. **`_maybe_trigger_cycle` の順序ずれ**(§2-3)。最後に置く。S9 cycle テストで固定。
3. **`parts` 統一による off-by-one**。各ブロックの `len(parts) >= N` ガードはそのまま移植。statement coverage を S5/S8/S9 の境界 topic で確認。
4. **payload in-place 変更の参照切れ**。抽出メソッドへ payload をコピーせず参照渡し(§2)。S0 先行テストで固定。
5. **ガード early-return の取り違え**。例: S5 の `inferred is not None` ガードを早期 return に変える際、`reconcile_presence` を inferred 確定後にのみ呼ぶ現挙動を保つ(全 MQTT で reconcile しない最適化が L118–120 コメントで明記されている)。S5「非対象 topic で reconcile が呼ばれない」テストで固定。
6. **debounce / dedupe state の複製**。`_heartbeat_debounce` は self 経由参照のまま。引数化して局所辞書にしない。

## 9. 実装 GO 前にユーザー判断が要る点

1. **抽出メソッドの命名**(§5.1 は案)。`MqttSyncMixin` の既存命名規約(snake + 動詞)に沿っているが、`_feed_schedule_learner_occupancy` 等が冗長なら短縮可。
