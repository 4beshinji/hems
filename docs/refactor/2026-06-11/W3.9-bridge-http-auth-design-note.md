# W3.9 設計ノート — ブリッジ HTTP エンドポイントへの `HEMS_INTERNAL_TOKEN` 認証横展開

対象: [`PLAN.md`](PLAN.md) W3.1 で作成した `hems_common.auth.verify_internal_token` を、9 ブリッジの REST endpoint に配線する。

背景: 2026-06-11 監査 S3 に挙げられ、PLAN.md では「W3.1 の共通ライブラリに同梱すると一括解消」と記載されたが、W3.2 移行 commit では MQTTPublisher / lifespan の共通化に留まり、**各ブリッジの FastAPI router には未適用**であった。

---

## 1. 現状確認

### 1.1 既存の認証実装

- **`services/stt/src/main.py:56-61`**: `_check_auth(authorization: str | None)`
  - `_INTERNAL_TOKEN` 未設定時は dev mode として認証スキップ
  - `Bearer ` prefix 除去後、`hmac.compare_digest` で定数時間比較
  - 不一致時 `HTTPException(401)`

- **`services/brain/src/brain_chat_server.py:29-43`**: `brain_auth_middleware`
  - 全 non-health エンドポイントで Bearer 検証
  - 同様に未設定時はスキップ

- **`services/_common/hems_common/auth.py`**: `verify_internal_token` がすでに存在
  - `Authorization: Bearer <HEMS_INTERNAL_TOKEN>` を検証する FastAPI dependency
  - 未設定時は no-op（戻り値 `None`）

### 1.2 未認証状態のブリッジ

9 ブリッジ（ha / gas / obsidian / biometric / switchbot / tapo / news / knowledge / weather）の `FastAPI` アプリおよび各 `APIRouter` には `verify_internal_token` が配線されていない。

```python
# 現状の例: services/weather-bridge/src/main.py
app = FastAPI(title="HEMS Weather Bridge")
```

これらは原則として Docker 内部 network / 127.0.0.1 運用であり外部露出はないが、同一ホスト・同一 Docker ネットワーク上の任意プロセスから到達可能な状態にある。

### 1.3 特殊ケース: biometric webhook

`biometric-bridge` は外部サービス（Zepp Life / Amazfit 等）からの webhook を受ける `/webhook/{vendor}` エンドポイントを持つ。これらは `BIOMETRIC_WEBHOOK_SECRET` で HMAC 検証しており、`HEMS_INTERNAL_TOKEN` とは目的が異なる。

- `BIOMETRIC_WEBHOOK_SECRET`: 外部クラウドサービスが webhook 送信時に署名する鍵
- `HEMS_INTERNAL_TOKEN`: HEMS 内部サービス間の信頼関係

→ webhook endpoint は `HEMS_INTERNAL_TOKEN` 検証の対象外とする。

## 2. 設計方針

### 2.1 基本ルール

| 対象 | 認証 | 理由 |
|---|---|---|
| 一般 REST endpoint (`/api/*`, `/devices/*` 等) | `verify_internal_token` 必須 | 内部サービス間通信の保護 |
| `/health` | 無認証維持 | Docker healthcheck / 外部監視からのアクセスを許可 |
| `/metrics`（あれば） | 無認証維持 | プロメテウス等の監視 |
| `biometric` `/webhook/{vendor}` | `BIOMETRIC_WEBHOOK_SECRET` のまま | 外部 webhook は内部 token を持たない |

### 2.2 zero-config 互換

`HEMS_INTERNAL_TOKEN` 未設定時は `verify_internal_token` が no-op となる（`_common` 実装済み）。これにより、既存の LAN-trusted 運用ユーザーの設定変更を強制しない。

ただし、新規導入時やセキュリティ重視時には `HEMS_INTERNAL_TOKEN` を設定することで即時保護が有効化される。

### 2.3 backend→bridge 呼び出し側

backend から bridge への呼び出し（既に backend → brain / voice / stt には付与済み）も `Authorization: Bearer <HEMS_INTERNAL_TOKEN>` を付与する必要がある。対象:

- backend → ha-bridge
- backend → tapo-bridge（存在すれば）
- backend → switchbot-bridge（存在すれば）

現状 backend が直接 bridge を呼ぶ箇所は限定的（主に ha-bridgeの `/devices/{id}/control` 等）。`services/backend/routers/home.py` 等を確認し、`_internal_headers()` ヘルパーを再利用する。

## 3. 実装パターン

### 3.1 ルーター全体に適用（推奨）

```python
from fastapi import Depends, FastAPI
from hems_common.auth import verify_internal_token

app = FastAPI(
    title="HEMS Weather Bridge",
    dependencies=[Depends(verify_internal_token)],
)
```

これにより全エンドポイントに一括適用でき、漏れを防ぐ。`/health` 等を除外したい場合は別途 `APIRouter` に分離する。

### 3.2 `/health` 分離パターン

```python
from fastapi import APIRouter, Depends, FastAPI
from hems_common.auth import verify_internal_token

public_router = APIRouter()          # /health, /metrics
private_router = APIRouter(dependencies=[Depends(verify_internal_token)])

app = FastAPI(title="HEMS Weather Bridge")
app.include_router(public_router)
app.include_router(private_router, prefix="/api")
```

現状 `/health` エンドポイントを持つブリッジは限定的（`ha-bridge` 等）だが、Docker healthcheck で使われるため無認証維持が必要。

### 3.3 biometric webhook 分離

```python
public_router = APIRouter()
public_router.add_api_route("/webhook/{vendor}", handle_webhook, methods=["POST"])

private_router = APIRouter(dependencies=[Depends(verify_internal_token)])

app = FastAPI(title="HEMS Biometric Bridge")
app.include_router(public_router)
app.include_router(private_router, prefix="/api")
```

## 5. テスト戦略

### 5.1 追加テスト

各ブリッジに以下を追加:

- token 未設定時: 通常通り 200 / 既存挙動維持

- token 設定時、誤った token: 401

- `/health` は token なしでも 200
- biometric のみ: `/webhook/{vendor}` は token なしでも `BIOMETRIC_WEBHOOK_SECRET` 検証下で動作

- `home.py` 等から bridge 呼び出し時に `Authorization` ヘッダが付与されることを確認

## 8. リスク・注意点

1. **healthcheck 破壊**: `/health` に誤って認証をかけると Docker によりコンテナが unhealthy になりうる。実装時は必ず分離。
2. **backend→bridge 呼び出し漏れ**: backend 側のヘッダ付与を忘れると、token 設定時に内部通信が 401 になる。
3. **biometric webhook 誤適用**: 外部サービスからの webhook に内部 token を要求すると連携が破壊される。
4. **stt/voice との重複**: stt/voice は既に独自 `_check_auth` を持つ。`verify_internal_token` へ統一するかは別途検討（本 row ではブリッジ 9 件のみ対象）。
