## 0. 結論サマリ(先読み)

- 「三重ソース」の実態は **二重定義(world_model 定数 / RuleThresholds dataclass)+ 一段の re-export(rule_engine.py 冒頭の UPPERCASE)** である。UPPERCASE は独立した第三定義ではなく、`RuleThresholds` フィールドを module attribute に展開した **facade re-export** にすぎない(`rule_engine.py:38-74`)。
- 真に独立した二重定義は **world_model.py の `CO2_HIGH` 系定数(`world_model/world_model.py:113-149`)と RuleThresholds(`rules/config.py`)が同じ env var を別々に読んでいる**点。値の不整合は現状ゼロ(後述 §2 の照合表)だが、env を片方だけ上書きすると不整合になりうる構造的リスクがある。
- **推奨 canonical source = `RuleThresholds`(`rules/config.py`)を唯一の SoT に昇格**。world_model 側定数は RuleThresholds から導出する。理由は §3。
- ただし **GO 前にユーザー判断が要る点が 3 つある**(§8)。最大の論点は「env var 名の重複(world_model と config が同名 `HEMS_THRESHOLD_*` を読む)を統合後どう一本化するか」。

### 2-C. 重複・不整合の検出結果

1. **同概念で env var 名が重複**(最重要): PM25 が **二経路で別 env var**。
   - サイト A `PM25_HIGH ← HEMS_THRESHOLD_PM25_HIGH`(default 35、zigbee.py:162 で参照)
   - サイト B `pm25_native_high ← HEMS_THRESHOLD_PM25_NATIVE`(default 35、別 rule で参照)
   - **値は両方 35 で一致**しているが、env で片方だけ変えると分裂する。「native」は perception 推定値 vs ネイティブ PM2.5 センサ値の区別が意図(コメントなし)。→ 統合可否はユーザー判断(§8-1)。
2. **値の不整合は現状なし**: 上記照合の結果、A と B で同名・同概念のフィールドはデフォルト値が一致(温度系は A=event 用 28/16、B=critical 用 40/5 で別概念のため衝突せず)。
3. **名前ブレ**: critical 系は world_model 側に存在せず RuleThresholds のみ。`TEMP_HIGH`(A、event 警告)と `temp_critical_high`(B、低電力危険)は別物 — **統合時に混同しないこと**。
4. **env.example の網羅漏れ**: サイト B 由来の env var(`HEMS_THRESHOLD_TEMP_CRITICAL_HIGH`, `HEMS_THRESHOLD_VOC_HIGH`, `HEMS_THRESHOLD_PM25_NATIVE`, `HEMS_PROC_CPU_HIGH`, `HEMS_DEVICE_BATTERY_LOW`, `HEMS_CIRCADIAN_*` 等)は **env.example に未記載**(grep で 0 件)。サイト A 由来(`HEMS_THRESHOLD_CO2_HIGH` 等)はコメントアウトで記載あり。W4.1 と整合させること。

## 3. canonical source の選定

**推奨: `RuleThresholds`(`rules/config.py`)を単一 SoT に昇格。world_model 側の閾値定数(サイト A の閾値分)は RuleThresholds から導出する。**

理由:
- RuleThresholds は **既に dataclass + ローダ + env 上書き + frozen** という SoT に必要な構造を備える。world_model 側は素の module 定数で、構造化されていない。
- 既存の DI 起点(`_rule_engine` facade)が RuleThresholds を中心に組まれており、mixin の DI パターン(§5)を RuleEngine と WorldModel の両方へ拡張する自然な延長線。
- world_model を SoT にすると rules → world_model の import 方向依存が強まり、W2.2(world_model mixin facade 脱結合)と矛盾する。RuleThresholds は両 mixin 群から見て中立な置き場。

**例外(SoT に入れないもの)**:
- `ENV_STALE_SEC` / `ZONE_BLIND_SEC`(freshness/degraded)は**閾値ではなく時間窓**で、W2.2 の方針では `brain_constants` 行き候補。本 row では **触らない**(scope 外、`brain_constants.py` の `RECENT_EVENT_WINDOW_SEC` 等と同類)。
- `circadian_curve` のハードコード曲線は RuleThresholds に既にある。維持。

代替案と棄却理由:
- **(却下)新規 `thresholds.py` を作り両者をそこへ集約**: 移行コストは RuleThresholds 昇格と同等だが、既存 import(`from rules.config import RuleThresholds`, `RULE_THRESHOLDS`)とテストを全部書き換える必要が増える。RuleThresholds 拡張のほうが差分が小さい。
- **(却下)world_model を SoT**: 上記 import 方向の問題。

## 4. 移行戦略(具体手順)

### 4.1 RuleThresholds への field 追加

サイト A の **閾値定数**(freshness 2 つを除く 21 個)を `RuleThresholds` に新フィールドとして追加し、`load_rule_thresholds()` に env 読み込みを移す。**env var 名・default 値・型は現行を一字一句維持**(§2-A の env/default をそのままコピー)。例:

```python
co2_high: int = ...           # HEMS_THRESHOLD_CO2_HIGH, 1000
temp_high: int = ...          # HEMS_THRESHOLD_TEMP_HIGH, 28  (critical とは別フィールド)
...
```

### 4.2 world_model.py 定数の導出化(後方互換 alias を残す)

`world_model/world_model.py:113-149` の各 module 定数を、env 直読みから **RuleThresholds 由来へ置換**。ただし `from . import world_model as _world_model; _world_model.CO2_HIGH` という facade 参照が世界モデル mixin 多数に存在するため、**module attribute は残す**:

```python
from rules.config import load_rule_thresholds
_WM_THRESH = load_rule_thresholds()
CO2_HIGH = _WM_THRESH.co2_high   # alias retained for _world_model.CO2_HIGH facade refs
...
```

→ これにより physical_updates / user_updates / digital_updates / context_builder / mqtt_router の `_world_model.X` 参照は **無改修**で動く(W2.2 で別途整理)。

### 4.3 rule_engine.py の re-export 維持

`rule_engine.py:17-33` の `from world_model.world_model import CO2_HIGH, ...` と `:38-74` の UPPERCASE alias は **そのまま残す**(後方互換)。mixin の `_rule_engine.CO2_HIGH` / `_rule_engine.HRV_LOW` 等(zigbee.py / biometric.py)が無改修で動く。

→ **本 row は「定義の単一化」だけを行い、参照側(mixin / world_model mixin)は触らない**。参照経路の整理は W2.2 / W2.3 の仕事。これが 1 row = 1 commit の blast radius を最小化する。

### 4.4 import 循環の確認(必須)

新たに `world_model/world_model.py` → `rules.config` の import が増える。現状の依存方向(`rule_engine` → `world_model.world_model` および `rules.config`)と衝突しないか確認。`rules/config.py` は `os` / `dataclasses` のみ import で他 brain module に依存しないため **循環は発生しない見込み**だが、`load_rule_thresholds()` を world_model import 時に呼ぶことで **import 順序により env が二回読まれる**点に注意(冪等なので値は不変、§6 でテスト)。

## 5. DI の形

現状の DI は **module facade**(`_rule_engine.X` / `_world_model.X`)であり、constructor 注入ではない。本 row では **このパターンを破壊しない**(破壊は W2.2/W2.3)。

- **本 row のゴール**: 「両 facade(`_world_model.*` 閾値定数 と `_rule_engine.*` 閾値定数)が、同一の `RuleThresholds` インスタンスから導出される」状態にする。物理的には §4.2 の `_WM_THRESH` と `rule_engine.py:34` の `RULE_THRESHOLDS` が **同じ `load_rule_thresholds()` の結果**を指す(値同一、インスタンスは別でも可)。
- **将来(W2.2/W2.3)の理想形**(本 row では実装しない、設計メモのみ): `RuleEngine.__init__(self, thresholds: RuleThresholds | None = None)` / `WorldModel.__init__(self, thresholds=...)` で受け取り `self.thresholds` 属性にし、mixin は `self.thresholds.co2_high` を参照。module facade を撤廃。本 row はその **前提となる単一 dataclass を確立する**ところまで。
- 互換: テスト(`test_rule_engine_thresholds.py`)が `importlib.reload(rule_engine)` で env 反映を検証しているため、**module-level の `load_rule_thresholds()` 呼び出しは維持必須**(constructor DI へ全面移行すると reload テストが壊れる)。本 row では維持する。

## 6. 挙動不変の保証方法

「値が一字一句変わらない」ことを担保する追加テスト案(GO 条件):

1. **全閾値スナップショット assert**(新規 `test_threshold_single_source.py`):
   - 移行前の commit で `RULE_THRESHOLDS` 全フィールド値 + world_model module の全閾値定数値を 1 個の dict にダンプ(固定の golden 値としてテストにハードコード)。
   - 移行後、同じ dict を再構築し golden と完全一致を assert。env 未設定状態で全 default 値を固定。
2. **A/B 同一性 assert**: `world_model.world_model.CO2_HIGH == RULE_THRESHOLDS.co2_high`(全ペア)を assert。統合後に両 facade が同値であることの恒久ガード。
3. **env 上書き保存テスト**: 既存 `test_rule_engine_thresholds.py` の reload パターンを流用し、サイト A 由来 env(`HEMS_THRESHOLD_CO2_HIGH=2000` 等)で reload → `world_model.CO2_HIGH == 2000` かつ `RULE_THRESHOLDS.co2_high == 2000` を確認。**env 上書き経路が壊れていないことの証明**。
4. **既存ゲート**: baseline 1283 passed を下回らないこと。特に `test_rule_engine_*`(critical/sustained/biometric/zigbee/home/services)と `test_freshness.py`(ENV_STALE_SEC/ZONE_BLIND_SEC import)が緑。

## 7. 影響範囲とリスク

- **触るファイル**: `rules/config.py`(フィールド追加 + ローダ拡張)、`world_model/world_model.py:113-149`(導出化 + alias 維持)。**実質 2 ファイル**。+ 新規テスト 1。`rule_engine.py` は **無改修**(re-export 維持)。mixin は **全て無改修**。
- **回帰リスク高**:
  - import 循環 / import 順序による env 二重読み(§4.4)。`world_model` import 時点で `rules.config.load_rule_thresholds()` を呼ぶのが初。
  - `test_rule_engine_thresholds.py` の `importlib.reload(rule_engine)` が world_model 側 alias を反映しない可能性(rule_engine だけ reload して world_model module をキャッシュしたままだと A/B が分裂)。→ §6-3 のテストで検出。**reload 対象に world_model も含める必要があるかもしれない**(要実装時確認)。
- **W2.2-W2.4 との順序依存**: 本 row は **W2.2(world_model mixin 脱結合)・W2.3(rules mixin 脱結合)の前提**。本 row で「単一 dataclass」を確立 → W2.2/W2.3 で「facade 撤廃 → `self.thresholds` DI」へ移行 → W2.4 で evaluate 分割。**逆順は不可**(facade を先に剥がすと参照元が単一ソースを持たない)。

## 8. 実装 GO 前にユーザーが判断すべき点

1. **PM25 の二 env var(`HEMS_THRESHOLD_PM25_HIGH` vs `HEMS_THRESHOLD_PM25_NATIVE`)を統合するか温存するか。** 値は両方 35 で一致するが概念が別(推定値 vs ネイティブセンサ)。統合すると env 互換 breaking。**推奨: 本 row では温存**(2 フィールドのまま単一ソース化)。意味的統合は別 row。

## 10. ユーザー決定(2026-06-11)とスコープ改定

§8 の 3 判断点に対するユーザー決定:
