## 0. 結論サマリ

- `cognitive_cycle` は **5 フェーズ**の直列実行: (A) `_run_preflight`、(B) `_run_fallback_guards`、(C) `_build_cycle_context`、(D) `_run_react_loop`、(E) `_postprocess_cycle`。Guard 群(B)は rule-only 経路として **early-return** し、LLM 経路(C–E)へ落ちない。
- **早期 return が 4 つ**(L245 / L252 / L260 / L268)と、context が空のときの bare-return(L272)。各 rule-only return は `_record_rule_cycle_summary` + `_push_all_snapshots` のペアで終わる(共通の後処理サブセット)。
- ReAct ループ(D, L438–537)は **iteration をまたぐ可変状態**が密(`messages` 蓄積、`tool_call_history`、`speak_count`、`consecutive_errors`、`total_tool_calls`、トークン累積)。これを**戻り値オブジェクトで受け渡す**のが分割の核心。
- **Guard 0–3 は ReAct ループ内**(tool フィルタリング、L452–491)であり、preflight の **fallback Guard(B)とは別物**。混同しないこと(§3 で峻別)。
- `cognitive_cycle` への**直接テストは現状ゼロ**(§5)。W2.6 と同じく characterization テストの先行追加が唯一の安全弁。
- **commit 分割を推奨**: (C1) characterization テスト → (C2) 抽出。W2.4 / W2.6 と同じ規律(§7)。

## 1. 現状構造 — 制御フローの段階分解

実装後の `cognitive_cycle` は 5 つの private メソッドを順に呼ぶ薄いオーケストレータ。

| Phase | 抽出メソッド | 責務 | 主な副作用 |
|---|---|---|---|
| **A** | `_run_preflight()` | cycle_start/カウンタ初期化、task_queue 処理、power mode 評価、presence/schedule refresh、SunriseAlarm 開始判定、scheduled wake_up fallback 発火、BootLoad 開始判定、`rule_engine.refresh_devices()` | task_queue、power_mode、world_model.user、sunrise start、wake_up trigger(create_task)、boot_load start |
| **B** | `_run_fallback_guards(cycle_start, total_tool_calls)` | low-power / VLM swap / GPU busy の各 Guard を順次評価。rule-only 経路なら early-return、escalate なら `low_power_escalation=True` で C へ | rule actions 実行(一部経路)、`low_power_escalation` フラグ、4 経路で early-return |
| **C** | `_build_cycle_context(low_power_escalation, total_tool_calls)` | `get_llm_context()`(空なら bare-return)、device summary、生活パターン、recent_events / actionable_reports / active_tasks / efficacy verdicts / action history を user_content に組み立て、system_msg 構築、`get_tools()` で tools 取得。返り値は `_ReactState` | 文字列組み立てのみ(`get_active_tasks` / `_get_cached_devices` は I/O)。`_ReactState` 生成 |
| **D** | `_run_react_loop(state)` | 最大 `REACT_MAX_ITERATIONS` 反復: LLM `chat` → response guard(error/no-tool で break)→ tool フィルタ(Guard 0–3)→ assistant msg append → tool 実行 → tool result msg append → error カウント | LLM 呼び出し、tool dispatch、`messages` 蓄積、`_action_history` append、ambient_speaker、alert suppress。state を in-place 更新 |
| **E** | `_postprocess_cycle(state, cycle_start)` | cycle summary 構築 + `_last_cycle_summary` 保存、`event_writer.record_decision`、action_history prune、`_push_all_snapshots`、Obsidian decision log writeback、ログ出力 | event_store persist、snapshot push、Obsidian write |

補足:
- **A は Guard より前に必ず走る**(power mode 評価が B の `is_low_power` 判定の前提)。`rule_engine.refresh_devices()` は全 Guard と LLM 経路が共通で使うため A の末尾に置かれている。
- **C 以降(C/D/E)は LLM 経路専用**。B のいずれかの Guard が return すると C–E に到達しない。
- B の escalate 分岐だけは return せず C へ落ち、`low_power_escalation=True` を C の user_content が読む。**B と C のデータ依存はこの 1 本のみ**。

## 2. 副作用と順序 — 分割で壊れる核心

### 2.1 LLM 呼び出し
- 唯一の発火点は **D の L439 `await self.llm.chat(messages, tools)`**、ループ内で最大 `REACT_MAX_ITERATIONS`(=5)回。
- B1 escalate 時に `power_mode_manager.record_llm_call()`(L229)が **1 回**呼ばれる(実 chat 呼び出しの前)。これは rate-limit 会計であり chat 呼び出し回数とは独立。**抽出後も B1 内に残す**。

### 2.2 tool dispatch
- rule 経路(B1–B3): `_run_rule_actions(...)`(L80–101)が各 action を `tool_executor.execute` で順に実行。
- LLM 経路(D): フィルタ後の `filtered` を L506–537 で `tool_executor.execute`。dispatch 順 = `filtered` の順 = LLM が返した tool_calls 順(Guard で間引いた後)。

### 2.3 world_model 更新
- A の `power_mode_manager.evaluate`、`_refresh_presence_and_schedule`(world_model.user 更新)、`suppress_alert`(D の `_suppress_alert_for_task`、L536–537)。

### 2.4 event_store 書き込み・decision 記録
- rule 経路: `_record_rule_cycle_summary`(L615–617)が `_last_cycle_summary` を更新するのみ(**event_writer へは書かない**)。
- LLM 経路: E で `_build_cycle_summary`(L588–613)→ `_last_cycle_summary` 保存 → `event_writer.record_decision`(L542–552、`total_tool_calls > 0` のときのみ)。
- **rule 経路と LLM 経路で後処理が分岐**: rule は summary 保存 + snapshot push のみ、LLM は加えて record_decision / prune / Obsidian。§3 参照。

### 2.5 speak 発火
- rule 経路: `_run_rule_actions` 内、`tool == "speak"` かつ success で `ambient_speaker.record_speak`(L91–92)。
- LLM 経路: D の Guard 2(L463–466)で `speak_count` 上限(`MAX_SPEAK_PER_CYCLE=1`)制御、実行後 success で `ambient_speaker.record_speak`(L534–535)。
- speak の persona rewrite / low-power gating は **tool_executor 側**(`_handle_speak`)に移管済み(L80–84 docstring)。本 row では触らない。

### 2.6 エラーカウンタ・cooldown
- `consecutive_errors`(D ローカル、L415 初期化): tool 失敗で +1、`MAX_CONSECUTIVE_ERRORS`(=1)到達で **inner for を break**(L528–531)。success でリセット(L533)。**iteration をまたいで保持**(ループ外で初期化、ループ内で更新)。
- rule cooldown は `rule_engine.evaluate` 内部の状態(本 row では触らない。W2.4 の対象)。`evaluate` は B1(L220)/ B2(L257)/ B3(L265)で呼ばれ、**呼ぶたびに cooldown を消費**する。B1 で normal rule scan として 1 回呼んだ後 escalate しても、その cooldown 消費は保存する必要がある(挙動不変)。

### 2.7 early-return / break / continue の位置(完全列挙)
| 種別 | 行 | 条件 | 後処理 |
|---|---|---|---|
| return | L245 | low-power throttled(rule 直接実行) | summary(`rule_low_power_throttled`)+ push |
| return | L252 | low-power idle(rule 未発火) | summary(`rule_low_power_idle`)+ push |
| return | L260 | VLM swap | summary(`rule_vlm_swap`)+ push |
| return | L268 | GPU busy | summary(`rule_gpu_busy`)+ push |
| return | L272 | `llm_context` 空(bare) | **後処理なし**(snapshot push もしない) |
| break | L444 | response.error or no tool_calls | ループ脱出 → E へ |
| break | L497 | filtered 空 | ループ脱出 → E へ |
| break | L531 | consecutive_errors 上限 | inner for 脱出(outer は継続するが次 iteration の chat へ) |
| continue | L456/460/464/480/491 | Guard 0–3 各種 | tool フィルタ内スキップ |

> 落とし穴: L272 の bare-return は **唯一後処理を一切しない return**。抽出時にここへ snapshot push を足すと挙動変化。要保存。

## 3. Guard ロジックの構造(2 系統あることに注意)

「Guard」が **2 つの異なる文脈**で使われている。設計で峻別する:

### 3.1 fallback Guard(preflight 後の rule-based 分岐 = Phase B)
LLM を回すか rule-based で済ませるかの**経路選択**。順序固定:

1. **B1 low-power**(L211–252): `power_mode_manager.is_low_power`。
   - critical rules は常に即実行(`evaluate_critical`, rewrite=False)。
   - normal rules scan(`evaluate`)が発火 **かつ** `allow_llm_call()` → escalate(C へ、`low_power_escalation=True`)。
   - 発火したが LLM throttled → rule 直接実行 + **return**。
   - 未発火 → **return**(LLM skip)。
2. **B2 VLM swap**(L255–260): `world_model.vlm_model_swap_active` → rule + **return**。
3. **B3 GPU busy**(L263–268): `rule_engine.should_use_rules()` → rule + **return**。

LLM 経路と rule 経路で**後処理が共通か分岐か**:
- 共通サブセット = `_build_cycle_summary`(両者が呼ぶ。rule は iterations=0、mode 違い)+ `_push_all_snapshots`。
- LLM 経路のみ = `event_writer.record_decision` + action_history prune + Obsidian writeback + ログ。
- → **後処理は「共通コア(summary + push)+ LLM 拡張」の 2 層**。抽出時、rule 経路は共通コアだけ呼び、LLM 経路は共通コア + 拡張を呼ぶ構造にする(現状の `_record_rule_cycle_summary` が共通コアの summary 部分を既に切り出している)。

### 3.2 tool Guard(ReAct ループ内のフィルタ = Phase D 内、L452–491)
LLM が返した tool_call を実行するか間引くか。`filtered` を組み立てる:

- **Guard 0 blind**(L454–456): `system_blind` かつ `name in BLIND_SUPPRESSED_TOOLS` → continue。
- **Guard 1 dup**(L459–460): `call_key in tool_call_history` → continue。
- **Guard 2 speak limit**(L463–466): `speak_count >= MAX_SPEAK_PER_CYCLE` → continue、else speak なら `speak_count += 1`。
- **Guard 3 create_task dedupe**(L470–491): active_tasks との title 部分一致 / 直近 action 履歴との一致 → continue。

これらは **iteration をまたぐ状態**(`tool_call_history`, `speak_count`, `active_tasks`, `_action_history`, `system_blind`, `now`)を読む。抽出するなら「1 つの tool_call を受けて (採用/スキップ) を返す」純関数化が可能だが、`speak_count` の副作用増分があるため戻り値で受け渡す設計が要る(§6.1)。

## 6. 抽出設計

### 6.1 抽出メソッド一覧(`CognitiveCycleMixin` の private メソッドとして)

ReAct ループ状態は dataclass `_ReactState` に束ね、ループ系メソッドで受け渡す:

```python
@dataclass
class _ReactState:
    messages: list
    tools: list
    active_tasks: list
    now: float
    system_blind: bool
    total_tool_calls: int = 0
    tool_call_history: list = field(default_factory=list)
    speak_count: int = 0
    consecutive_errors: int = 0
    iteration: int = 0
    prompt_tokens_total: int = 0
    completion_tokens_total: int = 0
    gpu_util_pct: float | None = None
```

| 抽出メソッド | 由来 Phase | 入力 | 出力 / 副作用 | 備考 |
|---|---|---|---|---|
| `_run_preflight()` | A (L138–208) | なし | task_queue/power/presence/sunrise/bootload 副作用、返り値なし | power 評価が B1 の前提なので**必ず最初** |
| `_run_fallback_guards(cycle_start) -> str \| None` | B1–B3 (L210–268) | cycle_start, total_tool_calls | rule 実行 + early path。**処理済みなら mode 文字列、LLM 継続なら None** を返す。`low_power_escalation` も返す(tuple or state) | return 4 経路をここに封じ、本体は `if mode: return` で締める |
| `_build_cycle_context(low_power_escalation) -> _ReactState \| None` | C (L270–436) | escalation フラグ | messages/tools/active_tasks/now/system_blind/gpu サンプルを詰めた `_ReactState`。`llm_context` 空なら **None**(= bare-return 相当) | I/O(`get_active_tasks`/`_get_cached_devices`)を内包 |
| `_filter_tool_calls(state, response) -> list` | D Guard 0–3 (L446–497) | state, response | 採用 tool_calls list、`state.speak_count`/`tool_call_history` を更新 | Guard 0–3 を 1 箇所に集約 |
| `_dispatch_iteration(state, filtered) -> bool` | D 実行部 (L499–537) | state, filtered | tool 実行、messages append、`_action_history` append、ambient/suppress、error カウント。**継続可否(error 上限 break)を bool で返す** | |
| `_run_react_loop(state)` | D ループ (L438–537) | state | LLM chat + filter + dispatch を反復。state を in-place 更新 | iteration / token 累積を state へ |
| `_postprocess_cycle(state, cycle_start)` | E (L539–566) | state, cycle_start | summary 保存、record_decision、prune、push、Obsidian、ログ | LLM 経路の拡張後処理 |

本体 `cognitive_cycle` は薄いオーケストレータになる(擬似):

```
cycle_start = time.time()
await self._run_preflight()
mode, escalation = await self._run_fallback_guards(cycle_start)
if mode is not None:        # B1 throttled/idle / B2 / B3
    return                  # (guards 内で summary+push 済)
state = await self._build_cycle_context(escalation)
if state is None:           # llm_context 空 (L272 bare-return)
    return
await self._run_react_loop(state)
await self._postprocess_cycle(state, cycle_start)
```

> 注意: `_run_fallback_guards` は **4 つの return + escalate fall-through** を内包する。設計上「mode 文字列を返したら本体が return、None なら LLM 継続」に統一し、summary/push を guard 内で完結させる(現状そうなっている)。escalate のみ `mode=None, escalation=True` で抜ける。

### 6.2 順序/副作用の保存方針

- **A → B → C → D → E の記述順 = 実行順**を本体で保証。とくに A の `power_mode_manager.evaluate`(L142)が B1 の `is_low_power` の前提。
- **B の rule cooldown 消費**(`evaluate` 呼び出し回数)を保存: low-power 経路で `evaluate` が **1 回だけ**呼ばれる現挙動(L220)を維持。B2/B3 も各 1 回。
- **L272 bare-return は後処理なし**を保存(`_build_cycle_context` が None を返したら本体が即 return、push しない)。
- **`total_tool_calls` は cycle 全体で累積**(A の rule 実行 + D の LLM tool)。guard 経路の rule 実行分も summary に乗るので、`_ReactState` ではなく **`_run_fallback_guards` の戻り値 + `_run_react_loop` の更新を合算**して E に渡す(rule 経路は E に来ないので問題は LLM escalate 後の合算のみ)。
- **`consecutive_errors` break は inner for のみ**(outer while は継続)を保存。`_dispatch_iteration` の bool 戻り値で「次 tool を実行するか」を制御し、ループ側で break。
- **Guard 2 の `speak_count` 副作用**を `_filter_tool_calls` 内で `state.speak_count` に反映(参照渡しの state を更新)。

## 7. characterization テスト方針(W2.5 の安全弁)

### 7.1 方針

分割**前**に `cognitive_cycle` の外部観測可能な振る舞いを固定するテストを `tests/test_brain_cognitive_characterization.py` に新規作成。`Brain` 全体は重いので `CognitiveCycleMixin` だけを mock subsystem で構成した軽量 harness を使う(W2.6 の `tests/test_brain_mqtt_characterization.py` を直接の参考形にする)。

harness 構成:
- **実 `WorldModel()`**(conftest の `world_model` fixture 再利用)を `self.world_model` に注入 → context 構築・blind 判定・suppress を実物で観測。
- **mock LLM client**: `self.llm` を、`chat(messages, tools)` で **固定の tool-call シーケンスを返す** stub にする。`LLMResponse(content, tool_calls, error, usage)` を返す。シナリオごとに「1 回目 speak 1 件 → 2 回目 tool_calls 空(自然終了)」等のスクリプトを差し込む。`self.llm.provider = "openai"`、`self.llm.model = "mock"`。
- **mock tool executor**: `self.tool_executor.execute = AsyncMock(return_value={"success": True, "result": "ok"})`。失敗シナリオは `success=False` を返させる。
- **mock rule_engine**: `evaluate` / `evaluate_critical` / `should_use_rules` / `refresh_devices` を MagicMock/AsyncMock。Guard 分岐の入力を制御。
- **mock power_mode_manager**: `is_low_power` / `allow_llm_call` / `evaluate` / `get_status` / `record_llm_call` / `seconds_until_llm_allowed`。
- その他 subsystem(`dashboard`/`event_writer`/`device_registry`/`schedule_learner`/`sunrise_alarm`/`boot_load_manager`/`task_queue`/`event_automation`/`automation_engine`/`ambient_speaker`/`timeline_generator`)は MagicMock/AsyncMock。`dashboard.get_active_tasks` / `fetch_all_devices` は AsyncMock。
- cycle ローカル state(`_action_history=[]`, `_scheduled_wake_fired_date`, `_recent_efficacy_verdicts=[]`, `_cached_devices`, `_TASK_ALERT_KEYWORDS`)を手で初期化。
- `asyncio.create_task` は monkeypatch or 実ループ。**`asyncio.create_task` を patch して「スケジュールされた coroutine 名」を記録**する方式(W2.6 の `run_coroutine_threadsafe` 捕捉と同型)が決定的で推奨。
- テストは `async def` + `pytest.mark.asyncio`(or anyio)。
