## 0. 結論サマリ(先読み)

- `evaluate`(`rule_engine.py:146-637`、約 492 行)は **2 種類のブロックが混在**している:
  1. **インライン未抽出ブロック** — zone ループ(151-483)内の env/occupancy 系 9 種 + zone ループ外の PC/VLM/heavy-proc/screen-time 系。これらは **まだメソッド化されていない実体コード**で、W2.4 の主対象。
  2. **既に mixin へ抽出済みの `_evaluate_*_rules(...)` 呼び出し列**(516-635)。W2.3 までで device_health / service_vip / gas / home / zigbee / circadian / absence / weather / biometric / perception / shopping は mixin 化済み。**ここは触らない**。
- したがって W2.4 の作業は「**zone ループ本体 + PC/VLM/heavy-proc/screen-time のインライン実体を、既存 mixin と同じ `_evaluate_*(self, world_model, now)` 規約のメソッドへ機械的に切り出す**」こと。設計の新規性はほぼなく、**回帰リスクの核心は (a) 発火順序の保存 (b) zone ループの共有 `now` と sustained tracker dict、(c) `datetime.now().hour` の二重呼び出し**にある。
- **挙動不変の最大の壊しやすさ**は「**zone ごとに 9 ブロックが順番に評価され、各 sustained tracker(`_voc_high_since` 等)を per-zone で更新する**」点。抽出単位を「ブロック単位の関数」にするか「zone 単位のオーケストレータ」にするかで設計が割れる(§2 で決定)。
- **既存テストは inline ブロックの約半分を覆っていない**(§3 照合表)。CO2 task / temp speak / humidity high・low / pressure-drop / soil-moisture / sedentary-event / screen-time / VLM-stuck に **直接 unit test が無い**。characterization テスト追加を GO 条件とする(§4)。
- **GO 前にユーザー判断が要る点が 2 つ**(§7)。最大の論点は「抽出粒度(per-block 関数 か per-zone オーケストレータ + サブ関数か)」と「1 commit か分割か」。

## 2. 発火順序の依存と共有状態(分割で壊れる核心)

### 2.1 「全部マッチ = 全部 append」モデル(先勝ちではない)

`evaluate` は **early-return を一切持たず**、マッチした全ルールの action を `actions` リストに **追記し続ける**(`return actions` は 637 のみ)。同一サイクルで複数ルールがマッチすれば **全部発火**する。よって:

- **抽出後も「各ブロックが独立に append する」順序を保てば結果は不変**。先勝ち制御は存在しないので、ブロック間の相互排除を気にする必要はない(唯一の例外は Z2 の temp high/low が `elif` で相互排他である点 — これはブロック**内部**の話で、Z2 を 1 メソッドに切り出せば保存される)。
- **順序が出力リストの並びに影響する**。`evaluate` の戻り値は順序付きリストで、呼び出し側(cognitive cycle / rule fallback)がこの順序に依存しうる。**抽出メソッドの呼び出し順を現行の上から下へ厳密に保つこと**が挙動不変の必要十分条件。

### 2.2 cooldown 更新タイミング(副作用が「判定時」に起きる)

`_check_cooldown*` 系(639-661)は **呼ばれた瞬間に `self._cooldowns[key] = now` を書き込む副作用がある**(チェックと set が同一メソッド)。したがって:

- ブロック内で `if cond and self._check_cooldown(...)` の **短絡評価順序**が重要。`cond` が False なら cooldown は更新されない(現行どおり)。抽出時に条件式の AND 順序を変えない限り保存される。
- **複数ブロックが同一 cooldown key を共有するケースが 1 箇所**: Z10 native PM2.5 が `f"zigbee_pm25_{zone}"`(394)を使い、zigbee mixin(`_evaluate_zigbee_sensor_rules`)の HA-binary PM2.5 ルールと **意図的に dedup key を共有**(コメント 391-392)。抽出後も **Z10 が zigbee mixin より先に評価される現行順序(Z10=zone loop 内 → M4 zigbee=607)を保つ**こと。順序を逆転させると「どちらが先に cooldown を消費するか」が変わり、発火デバイスが変わりうる。**これが最も見落としやすい落とし穴**。

### 2.3 sustained tracker dict の per-zone set/pop

Z7 / Z9 / Z11 / P3 は tracker dict(`_low_pressure_since` / `_voc_high_since` / `_low_light_since` / `_high_light_since` / `_heavy_proc_since`)を持つ。挙動不変に必須の不変条件:

- **「閾値超過で set、正常域で pop」の else 分岐を必ずセットで抽出する**(例: Z9 の `else: self._voc_high_since.pop(zone, None)` を落とすと tracker が永久に残り、二度と sustain がリセットされない)。
- Z7 の **`_pressure_history[zone] = env.pressure` は無条件書き込み**(258-259、cooldown 判定の前)。これを cooldown ブロック内に移すと「気圧降下検知の前回値更新」が止まる。**Z7 抽出時にこの行の位置を厳守**。
- P3 の **GC ループ(585-588)は zone ループ完了後・全 proc 走査後に 1 回**実行される。`seen_names` はブロックローカル。P3 を 1 メソッドに切り出せば `seen_names` ごと内包され保存される。

### 2.4 `now` と `datetime.now().hour` の扱い

- `now = time.time()`(149)は `evaluate` 冒頭で 1 回取得し全ブロックで共有。**抽出メソッドには `now` を引数で渡す**(既存 mixin 規約 `_evaluate_*(self, world_model, now)` と一致)。冒頭で 1 回取得を維持すれば、同一サイクル内 cooldown 判定が同一基準時刻を使う現行挙動が保たれる。
- **`datetime.now().hour` は 413(照度)と 467(深夜 idle)で 2 回別々に呼ばれる**。秒境界をまたぐと両者が異なる hour を見る理論上の差異があるが、現行も別呼び出しなので **抽出時も別々に呼べば挙動不変**(統一して 1 回にするのは「挙動改善」であって W2.4 のスコープ外 — やらない)。

## 5. 抽出するメソッド一覧(設計)

### 5.1 粒度の決定

2 案を検討した:

- **案 A(per-block)**: Z1..Z13 を各々 `_evaluate_*` メソッド化し、zone ループ内で 13 個呼ぶ。→ メソッド数が多く、各 sustained tracker の per-zone 出入りが分散して逆に追いにくい。zone ループの二重(`for zone` を残しつつ各メソッドへ `(zone_id, zone, now)` を渡す)構造になる。
- **案 B(zone オーケストレータ + サブ抽出)**: zone ループ本体を `_evaluate_zone_environment(self, zone_id, zone, now)` 1 メソッドに切り出し、その内部を論理サブ(`_eval_env_thresholds` / `_eval_sustained_env` / `_eval_occupancy`)へ更に分ける。loop 外は `_evaluate_pc_rules` / `_evaluate_screen_time` / `_evaluate_vlm_swap` に分離。`evaluate` 本体は「zone ループで `_evaluate_zone_environment` を呼び、loop 外メソッドと既存 mixin 呼び出しを並べるだけ」の薄いオーケストレータ(~40 行)になる。

**推奨は案 B**。理由: (1) 既存 mixin が既に「`_evaluate_*_rules(world_model, now)` を `evaluate` から並べ呼びする」形なので、案 B は同じ形に zone 系を寄せられて一貫する。(2) sustained tracker の set/pop が「同じサブメソッド内に閉じる」ので §2.3 の落とし穴を構造的に防げる。(3) `evaluate` の見通しが「全 domain の呼び出し台帳」になる。

  actions.extend(self._evaluate_screen_time(world_model, now))

  **注意**: 現行は P3(heavy proc 540-588)が M1/M2(device_health 516 / service_vip 518)と V1(521)より**後**にある。`_evaluate_pc_rules` に P1+P2+P3 を束ねると、P1/P2 は M1 より前、P3 は M1 より後という現行順序が崩れる。§2.1 の順序保存に抵触する。**回避策**: `_evaluate_pc_rules` を P1+P2 のみとし、P3 を別 `_evaluate_heavy_processes` にして V1 の後に呼ぶ。または P1/P2/P3 を 1 メソッドにまとめたうえで「束ねた結果の append 位置」を P1 の現行位置(516 直前)に置く — この場合 P3 が M1/M2/V1 より前にずれる。**どちらも出力リストの並びが変わる**。§4.2 のオーダリング・ゴールデンが必須なのはこのため。安全側は「**P1/P2/P3 を個別の `_evaluate_*` にして現行の出現位置を 1:1 で保つ**」。表の `_evaluate_pc_rules` 集約は見た目優先で、順序保存とトレードオフ。**§7 でユーザー判断**。

## 6. 1 commit か分割か

**分割を推奨(3 commit)**:

1. **commit 1: characterization テスト追加のみ**(§4.1+4.2)。現行 god-method に対して緑。挙動不変の「証拠」を先に固定する。レビューで「これが正しい現行挙動か」を独立に確認できる。
2. **commit 2: 抽出本体**(`evaluate` → zone/pc/vlm/screen-time メソッド + 新 mixin)。テストは commit 1 のものが緑のまま。
3. **commit 3(任意・§7 で GO した場合): `evaluate_critical` の同型抽出**。

理由: テストと抽出を同一 commit にすると「テストが抽出後の挙動に合わせて書かれた(=回帰を見逃す)」疑いを排除できない。**先にテストを固定**するのが characterization refactor の定石。W2.1 design note と同じく挙動不変 row なので手動疎通は不要、テスト緑が GO 条件。

## 7. GO 前にユーザー判断が要る点

1. **抽出粒度(案 A per-block vs 案 B zone オーケストレータ)**。本書推奨は案 B。ただし mixin を新設(`rules/environment.py` / `rules/pc.py`)するか `RuleEngine` 本体メソッドに留めるかは設計趣味の領域。**新 mixin を作ると W2.3 の構成と一貫するが、ファイル数が増える。**
2. **PC ブロックの順序保存 vs 集約の見た目**(§5.2 末尾)。P1/P2 と P3 は現行で M1/M2/V1 を挟んで分離している。これを 1 メソッドに束ねると **出力 action リストの並びが変わる**。「並び順は呼び出し側にとって意味を持つか?」を確認したい。意味を持たない(集合として扱う)なら集約してよい。少しでも意味を持つなら個別抽出で 1:1 順序維持。**安全側 = 個別抽出**。
3. **`evaluate_critical`(147 行)を W2.4 に含めるか**(§1.3)。PLAN は名指ししていないが同型 god-method。**推奨は含める**(critical 系テストが厚く低リスク)。含めない場合は別 row 化の要否を PLAN に追記すべき。

## 8. 触るファイル / 回帰リスク / 想定外の落とし穴

**触るファイル**:
- `services/brain/src/rule_engine.py`(`evaluate` 本体、抽出元)
- (新設する場合)`services/brain/src/rules/environment.py`, `services/brain/src/rules/pc.py` + `RuleEngine` の mixin 継承リスト(`rule_engine.py:58-67`)に追加
- `tests/test_rule_engine_environment.py`(新規)

**回帰リスク(高→低)**:
1. **Z10 ⇄ zigbee mixin の cooldown key 共有**(`zigbee_pm25_{zone}`)。抽出で Z10 と M4-zigbee の評価順が入れ替わると発火デバイスが変わる。→ §4.1 の順序ガードテスト。
2. **sustained tracker の else-pop 欠落**(Z7/Z9/Z11/P3)。set だけ抽出して pop を落とすと永久 sustain。→ 各 sustained を 1 サブメソッドに閉じる(案 B)+ §3 で緑の既存 sustained テスト。
3. **action リストの並び順変化**(§5.2-2)。→ §4.2 オーダリング・ゴールデン。
4. **Z7 `_pressure_history` 無条件書き込みの位置移動**。cooldown ブロック内に誤って移すと前回値更新が止まる。
5. **Z2 temp の `elif` 排他**を `if/if` に書き換えると high と low が同時発火しうる(物理的にはありえないが論理回帰)。

**想定外の落とし穴**:
- `import random` / `datetime` / `parse_iso_ts`(`rule_engine.py:7,10,14`)は **mixin が使うため `# noqa: F401`** で残されている。新 mixin に move する際、これらの import を新ファイルに正しく持っていかないと NameError。
- `_get_devices` / `_device_is_on` / `_make_action`(108-135)は `RuleEngine` 本体メソッド。新 mixin から `self._get_devices(...)` で呼べるが、**mixin 単体テストで `RuleEngine` を継承せず mixin だけインスタンス化することはできない**(W2.3 が facade を撤廃し DI 化したのと同じ前提 — テストは必ず `RuleEngine` を生成する)。
- `datetime.now()`(413, 467)は **tz-naive `datetime` の `.hour`**。テストで `freezegun` 等を使う場合 UTC ではなくローカル時刻に依存する点に注意(既存 occupancy テストは `monkeypatch` で `datetime` を差し替えている — §3 の test_rule_engine_occupancy のパターンを踏襲)。
